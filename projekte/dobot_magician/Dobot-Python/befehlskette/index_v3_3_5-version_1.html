Wo stehen wir?

Die Befehlskette verbindet das Dobot-Steuerprogramm auf dem PC mit einem ESP32 oder einem ESP-Simulator. Die stabile Version v3.3.5 bildet den Ausgangspunkt.

Was ist neu?

OpenAI Codex wurde in die Entwicklung einbezogen. Codex analysiert die Projektdateien, nimmt gezielte Änderungen vor, führt mögliche Tests aus und dokumentiert die Ergebnisse.

Was mache ich?

Ich formuliere Anforderungen, baue Sensoren und Aktoren auf, übertrage Programme auf den ESP32 und prüfe das reale Zusammenspiel mit dem Dobot.

Die Geschichte des Projekts

Diese Seite dokumentiert nicht nur Programme. Sie zeigt auch, wie sich meine Arbeitsweise mit künstlicher Intelligenz Schritt für Schritt verändert hat.

  1. Eine verständliche Befehlskette entsteht

    Gemeinsam mit ChatGPT wurde aus einzelnen Dobot-Befehlen ein übersichtliches System. Die Befehle werden als gut lesbare Tupel notiert und vor der Ausführung geprüft. Dadurch bleibt der Programmablauf auch für Schülerinnen und Schüler nachvollziehbar.

  2. Der ESP32 wird einbezogen

    Zusätzlich zur Robotersteuerung entstand eine Kommunikation mit dem ESP32. Taster, LEDs, Sensoren und weitere Komponenten können dadurch in die Befehlskette eingebunden werden.

  3. Die Version v3.3.5 wird zum Ausgangspunkt

    Die Projektdateien, die Dokumentation und ein schrittweiser Einstieg wurden zu einem nachvollziehbaren Entwicklungsstand zusammengeführt. Diese Version bleibt als unveränderte Referenz erhalten.

  4. OpenAI Codex kommt hinzu

    Auf Anregung von ChatGPT habe ich OpenAI Codex mit dem vollständigen Projektpaket arbeiten lassen. Codex konnte die zusammengehörenden Dateien untersuchen und den geplanten Ablauf direkt am Projekt erklären.

  5. Eine Endloskommunikation wird gefunden

    Beim gemeinsamen Test von PC-Programm und Simulator entstand eine endlose Folge gegenseitiger Antworten. Codex analysierte die Ursache, änderte die Kommunikationslogik und ergänzte interne Versionsnummern.

  6. Der DHT11 wird zur ersten Erweiterungsaufgabe

    Als nächster Schritt erhielt Codex die Aufgabe, einen DHT11-Sensor in das Projekt einzubinden. Damit begann eine neue Form der Zusammenarbeit: Ich beschreibe die praktische Aufgabe, Codex bearbeitet die Software und ich teste das Ergebnis an der realen Hardware.

Praktischer Testablauf

Der Test erfolgt bewusst in kleinen Stufen. So lässt sich ein Fehler leichter einer einzelnen Komponente zuordnen.

  1. Einzelne Hardwarekomponente testen: beispielsweise den DHT11 mit einem kleinen Testprogramm auf dem ESP32.
  2. ESP32-Programm allein testen: direkt in Thonny, noch ohne Verbindung zum PC-Steuerungsprogramm.
  3. PC-Programm vorbereiten: Kommunikationsmodus und die tatsächlich verwendeten COM-Ports kontrollieren.
  4. COM-Port freigeben: Thonny auf „Lokales Python“, WebREPL oder einen anderen Anschluss umstellen beziehungsweise Thonny schließen.
  5. ESP32 neu starten: das Hauptprogramm muss auf dem ESP32 als main.py gespeichert sein.
  6. Kommunikation ohne Dobot-Bewegung prüfen: Meldungen, LEDs, Taster und Sensorwerte kontrollieren.
  7. Gesamtsystem testen: erst danach PC, ESP32 und Dobot gemeinsam betreiben.
Wichtige Einstellungen im PC-Programm 
COM_MODUS = "serial"       # "serial" oder "tcp"
DOBOT_PORT = "COM10"       # tatsächlichen Dobot-Port eintragen
ESP32_COM_PORT = "COM26"   # tatsächlichen ESP32-Port eintragen
ESP32_COM_BAUDRATE = 115200

Die COM-Portnummern sind Beispiele und müssen vor jedem Test mit dem Windows-Geräte-Manager beziehungsweise mit Thonny abgeglichen werden.

Mein erster Testplan mit Codex

Das ESP32-Programm wird auf den Mikrocontroller übertragen und als main.py gespeichert. Danach wird der von Thonny belegte COM-Port freigegeben, der ESP32 neu gestartet und das PC-Programm im seriellen Modus ausgeführt. Wichtig ist, dass Thonny und das Steuerprogramm den ESP32-Port nicht gleichzeitig geöffnet haben.
